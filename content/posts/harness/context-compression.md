> 本文根据个人提供的《harness 压缩》分享转录整理。原分享以 Claude Code 的设计作为讲解例子；以下内容主要复述其思路，不代表对 Claude Code 内部实现细节的独立审计或验证。

## 一、上下文压缩不只是让模型写摘要

常见理解是：当 Agent 的上下文快满时，让模型总结之前的对话，再用摘要替换历史消息。

分享提出了一个不同的工程视角：**语义摘要可以是最后的兜底步骤，而不是第一选择。** 在调用摘要模型之前，Harness 还可以从消息历史和工具结果入手，减少真正不再需要的内容。

这背后的原则是：

- 能保留原始消息，就尽量保留原始消息。
- 能清除无用的工具结果，就不必总结整段历史。
- 能裁剪无关片段，就不要改写仍然有用的内容。
- 能折叠并保留原文位置，就不一定要把整段内容重新压缩。

## 二、一次模型请求由哪些信息组成

分享把一次简化的模型请求拆成以下部分：

1. **System**：Agent 的定位，例如它是一个 Coding Agent。
2. **Rules**：需要遵守的规则，例如用户级规则、项目级规则，以及项目中已有的约定。
3. **Environment**：当前运行环境信息，例如工作目录及任务执行过程中的环境状态。
4. **Memory**：记忆检索系统提供的长期记忆或相关信息。
5. **Messages**：用户消息、Assistant 回复、工具调用（Tool Use）和工具返回结果（Tool Result）等消息历史。
6. **Tools**：当前任务可以使用的工具定义，例如读取文件、运行脚本等。

这里需要区分“请求包含什么”和“应该压缩什么”。分享认为，Agent 定位、规则、环境信息和记忆检索信息通常相对稳定、体量较小，或有各自的更新机制，因此不是上下文压缩优先处理的对象。

真正容易在多轮交互中不断累积、造成上下文膨胀的，是 **Messages，尤其是 Tool Result**。

## 三、为什么消息历史是压缩重点

一次工具调用可能读取一个很大的文件，返回成千上万个 Token。即使这个结果只在某一轮被读取一次，它也可能长期留在消息历史中，持续占用上下文。

多轮对话中，用户消息、模型回复、工具调用和工具结果反复叠加，容易出现冗余。因此，压缩策略应先判断哪些消息仍然对当前任务有价值，而不是简单地按时间删除旧消息。

## 四、四种工程层面的压缩方式

### 1. 删除无关消息（Message Pruning）

对话中可能夹杂着与当前任务无关的临时问题、解释或探索。例如，用户曾经询问一个概念，但这段讨论与当前正在执行的项目任务没有关系。

如果确认删除这部分内容不会影响当前任务，就可以从消息历史中移除它们。

需要注意：**不能简单地只保留最近 N 条消息。** 用户在较早阶段提出的目标、约束或禁止事项，可能需要贯穿整个任务。按时间截断容易误删仍然有效的信息。

### 2. 控制工具输出大小（Tool Output Truncation）

工具返回内容可能是上下文膨胀的重要来源。可以在工具层控制返回规模：

- 原本返回约 1000 个 Token，可以先返回其中约 500 个 Token。
- 同时告知模型还有哪些内容未展示，以及需要时去哪里读取。
- 让模型在确实需要时再按需获取剩余内容。

这不是丢弃全部信息，而是把完整读取改成“先返回必要部分，需要时再深入读取”。

### 3. 移除不再有用的工具结果（Tool Result Removal）

有些工具调用只是中间探索。工具返回了一大段内容，但后续任务已经不再依赖它。

如果确认该结果对后续执行没有持续影响，就可以从消息历史中移除。未来如果又需要同一信息，再次调用工具读取即可。

这种方式的重点是判断工具结果的生命周期：不是所有曾经读取过的内容都必须一直留在上下文里。

### 4. 折叠上下文（Context Folding）

有些探索结果当前暂时用不上，但未来可能再次需要。例如，已经梳理过某个项目文件的功能逻辑，当前步骤不依赖它，但后续步骤可能会用到。

这时可以不在上下文中保留全部原始内容，而是折叠成一条简短索引，说明：

- 折叠了哪些信息；
- 这些信息未来可能有什么用途；
- 如果需要完整内容，应该去哪里读取原文。

这样既减少当前上下文占用，也保留了重新获取信息的路径。折叠并不等于彻底删除：关键是保留原文位置，支持按需回读。

## 五、语义压缩作为最后兜底

完成上述工程处理后，如果上下文仍然过大，再考虑调用模型进行语义压缩。

分享中提到，摘要可以围绕一些具体维度组织，而不是只写一段泛泛的概述，例如：

- 用户最初的目标是什么；
- 已经尝试过哪些方案；
- 每次尝试得到什么结果；
- 哪些行为被禁止或明确不应尝试；
- 用户鼓励哪些行为；
- 已修改或涉及哪些文件，它们位于什么目录；
- 用户下一步希望做什么。

这种摘要质量会受到压缩模型能力和摘要维度设计的影响。对 Harness 而言，摘要结构应结合具体业务任务来设计。

## 六、工程取舍与风险

四种工程策略并不意味着一定不会丢失信息。删除、截断、移除工具结果和折叠上下文，都依赖 Harness 对任务状态与信息价值的判断。

设计时至少要考虑：

1. **约束是否保留**：早期用户指令可能长期有效，不能因消息较旧就删除。
2. **是否可回读**：截断或折叠时，应保留剩余内容的读取位置。
3. **删除是否可恢复**：对未来可能需要的探索结果，优先考虑折叠或可重新读取的设计。
4. **摘要是否结构化**：确需语义压缩时，应明确要求保留目标、尝试、结果、约束、文件和下一步计划等维度。
5. **压缩是否影响任务进度**：压缩策略最终要服务于任务连续性，而不只是降低 Token 数量。

## 七、总结

这段分享的核心观点可以概括为：

> 上下文压缩应优先从 Harness 工程层面减少冗余，语义摘要放在后面作为兜底。

建议的处理顺序是：

1. 识别并删除与当前任务无关的消息；
2. 控制工具输出的大小，支持按需读取；
3. 移除已经不再有用的工具结果；
4. 将暂时不用但未来可能需要的信息折叠，并保留原文位置；
5. 如果仍然超出上下文预算，再进行结构化语义压缩。

真正成熟的 Agent 系统，不只是会“总结历史”，还要能够判断哪些信息必须保留、哪些可以延迟读取、哪些可以丢弃，以及哪些内容需要保留索引以便恢复。
